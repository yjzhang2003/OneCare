## 0. 先说清楚：我们和参考文档不是同一种东西

参考文档是一个**多维表格配置类**案例——能力全部长在 Base 里（AI 字段捷径 + 自动化流程 + 仪表盘），所以它的「实践详述」每一节配的都是**配置界面截图**。

我们不是。OneCare 是一套**跑起来的系统**：飞书多维表格只是数据底座，上面有

- 一个自建 Web 运营工作台（Next.js + Postgres 镜像）
- 一个飞书机器人（Card 2.0 工单流转 / 拉群协同 / 群内问答）
- 一条 aily 打标流水线（Cron 分片 + 网页手动触发）

这决定了两处必须偏离参考文档：

| | 参考文档 | 我们 |
|---|---|---|
| 「实践详述」的配图 | 配置界面截图为主 | **运行中的界面为主**（工作台、飞书卡片、真实群聊） |
| 证明「AI 真的在跑」 | 截图上有 AI 字段的结果 | **录屏拍一次真实调用**（立即分析 ≈ 23 秒出结果） |

我们的优势就在这里：参考文档只能给结果截图，我们能给**过程**。所以录屏不是补充材料，是主证据。

#### 方案价值
[Before / After 两栏 + 数据测算 callout。

**Before**：人工读评价、无统一打标口径、跨部门靠转发、没有停留时长与超时口径、无法回答「这个设备是不是第三次报修」。
**After**：五个队列自动分流、AI 打标 + 规则 triage、工单卡片直接在飞书里流转、超时按 SLA 标记、用户/设备维度可聚合可预警。

### 二、实践详述

[开头照抄参考文档的做法：**demo 直达链接** + 一张整体架构图（展厅「闭环架构」章节现成的三层图可以直接截）。]

#### 2.1 真实 VOC 落库与字段校准
[对应参考文档的「数据爬虫 → 多维表格」。我们没有爬虫，**如实说**：数据来自企业周报 Excel，运营在多维表格里导入；字段与枚举已对真实 Base 校准（渠道 3 类 / 品类 / 事业部 13 个 / 问题分类一级 8 类 / 来源单号）。
**要讲的一个亮点**：原始周报 20 列，首次导入只映射了 5 列，后来补回 5 列并全量回填 3628 条——其中 `来源单号` 带来的是能力而不只是一列：3629 行只有 2773 个不同单号，约 856 行与其他行共用同一个来源工单，所以详情页能显示「另有 N 条同单号」。
配图：多维表格 VOC 记录表全貌 + 字段配置。]

#### 2.2 AI 打标（aily 技能）
[对应「AI 分析 VOC 情绪标签」。
- **AI 能力** callout：情绪极性（好评/中评/差评）、问题维度（7 类）、AI 摘要、AI 回复话术（多套语气）；
- **双轨设计**：飞书 aily 技能（A 轨）与多维表格 AI 字段捷径（B 轨）二选一，由 `TAGGING_PROVIDER` 切换，两轨产出**同一份打标结果契约**——参考文档只有 B 轨，这是我们比它多的一层；
- **建单与否不写在提示词里**：`triage()` 是仓库里的规则（差评→建单；中评+有维度→建单；其余→无需跟进），所以 AI 换了模型也不会改变业务判定；
- **实测**：单条 ≈ 23 秒；一次 5 条的批量会到 36.5 秒甚至 504，所以分片大小定为 1 条/次。
录屏：**S3（见下）**。]

#### 2.3 工单流转：五个队列 + 状态机
[对应「差评工单流转」。
- 状态机 `待分析 → 已分析 → 待跟进 → 跟进中 → 待闭环 → 已闭环`（+ 无需跟进 / 分析失败两条支线），含幂等与重试上限；
- 五个队列：待处理 **226** / 超时风险 **139** / 未分配 **13** / 分析异常 **20** / 全部 **3628**；
- 超时判据是**假设 SLA 72 小时**，不是海信合同值，界面上标注了；
- 负责人路由含兜底：解析不到负责人时不会把工单写进死胡同。
配图 + 录屏：**S2、S4**。]

#### 2.4 飞书卡片内闭环
[对应「负责人收到工单提醒并开始跟进」。我们比参考文档强的地方：**卡片里就能完成整条流转**，且服务端在同一次同步响应内做三重校验（记录存在 / 操作者是负责人 / 状态转移合法），任一不过就拒绝并回复明确提示，不写任何数据。
录屏：**S5**。]

#### 2.5 高严重度自动拉群协同
[参考文档没有这一层，是我们的差异点。高严重度记录进入待跟进时，自动向兜底人推送升级卡片 → 点「确认拉群」→ 建群、把工单卡发进群、群 ID 回写记录（同一条工单只会被提请一次）。群内 @机器人 可基于 Base 事实问答，闭环时产出群聊纪要。
录屏：**S6**。]

#### 2.6 用户画像 / 设备预警
[参考文档完全没有的一层。
- 用户画像：600 个多次反馈用户（共 2772 个标识）——性格与沟通倾向标签（强烈不满 / 陈述详尽 / 连续追问 / 夜间反馈 / 易升级 / 聚焦某维度）+ 关注度 + 建议动作；
- 设备追踪：206 台重复报修设备（共 854 台）——预警等级 + 复发判断（短期复发 / 疑似维修未彻底 / 疑似批次质量）+ 处置建议；
- 两页都能**一键拉群**，群里第一条消息就是这份分析。
⚠️ **必须标注**：这两处目前是**规则引擎**，不是模型——界面上和群卡片上都写着「由 规则引擎 生成」。文档里也要这么写，并说明 `ProfileInsightProvider` 这个接缝就是留给 aily 技能的（换实现是改一处绑定）。
录屏：**S7**。]

#### 2.7 实时看板
[对应「评价处理实时看板」。7 个指标 + 5 张分布图（闭环漏斗 / 打标进度 / 情绪极性 / 问题维度 / 渠道），全部由 SQL 聚合，不是全表扫内存。
可以顺带讲工程侧的一件事：读路径从多维表格迁到 Postgres 镜像后，整页从 2.6 秒降到 125ms，全表读 8.9s → 单页查询 947ms / 计数 116ms。
配图：**S2** 的第一屏。]

#### 2.8 提升点（照抄参考文档的诚实姿态）
[参考文档专门写了一段「当前 Base AI 分类打标准确度还有较大提升空间」。我们也写，而且要写全：
1. 用户画像 / 设备预警目前是规则引擎，aily 技能未做（接缝已留）；
2. 演示数据集的**时间轴与多数打标是合成的**——企业周报只给日期不给时刻，且是半年前的数据，直接展示会变成「3612/3628 全部超时」这种无意义画面；合成规则、备份与还原方式见 README，合成记录一律盖 `打标来源 = demo-seed`，真实 aily 打标的 19 条整条保留；
3. 打标吞吐受 aily 单条 23 秒限制，全量重跑不现实。
**这一节不要删。** 评委看得出哪些是演示数据，主动说清楚比被问出来强。]

### 拍之前必须先确认的四件事

1. **登录态**：用飞书客户端进（`/enter`），别用本地 mock session 出镜。
2. **数据前置**：S3 要有 `待分析`、S6 要有未拉群的 `严重度=高`——拍完 S3 那条就不再是待分析了，**同一条别重复用**。
3. **群会真的建**：S6 / S7 的拉群会在同事飞书里生成真实群聊并把未闭环工单的负责人拉进去。先跟组员说一声，或先约定用哪个标识拍。
4. **诚实边界**（口播和字幕都别越线）：
   - 画像 / 设备预警说「规则引擎」，不要说 AI；
   - 演示数据的时间轴和多数打标是合成的，要展示真实 AI 产出就开 S12 那几条；
   - 超时 SLA 72 小时是假设值，人工 5 分钟/条也是假设值。
