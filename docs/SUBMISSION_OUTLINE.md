## 0. 先说清楚：我们和参考文档不是同一种东西

参考文档是一个**多维表格配置类**案例——能力全部长在 Base 里（AI 字段捷径 + 自动化流程 + 仪表盘），所以它的「实践详述」每一节配的都是**配置界面截图**。

我们不是。OneCare 是一套**跑起来的系统**：飞书多维表格是数据底座，上面有自建 Web 运营工作台（Next.js + Postgres 镜像）、飞书机器人（Card 2.0 工单流转 / 拉群协同 / 群内问答）、一条 aily 打标流水线（Cron 分片 + 网页手动触发）。

两处必须偏离参考文档：

| | 参考文档 | 我们 |
|---|---|---|
| 「实践详述」的配图 | 配置界面截图为主 | **运行中的界面为主**（工作台、飞书卡片、真实群聊） |
| 证明「AI 真的在跑」 | 截图上有 AI 字段结果 | **录屏拍一次真实调用**（立即分析 ≈ 23 秒出结果） |

我们的优势就在这里：参考文档只能给结果截图，我们能给**过程**。所以录屏不是补充材料，是主证据。

#### 方案价值
[Before / After 两栏 + 数据测算 callout。

**Before**：人工读评价、无统一打标口径、跨部门靠转发、没有停留时长与超时口径、无法回答「这台设备是不是第三次报修」。
**After**：五个队列自动分流、AI 打标 + 规则 triage、工单在飞书卡片里直接流转、超时按 SLA 标记、用户/设备维度可聚合可预警。

**数据测算**（线上真值，假设必须标出来）：
- 累计 **3628** 条真实 VOC，已打标 **3110**（86%），打标成功率 **99%**
- 已建单 **880**，已闭环 **654**，**闭环率 74%**，平均闭环时长 **39 小时**
- 人工基线按**假设** 5 分钟/条 → 已打标部分约合 **259 小时**
  ⚠️ 5 分钟是**声明的假设不是实测**——代码里就叫 `ASSUMED_MANUAL_MINUTES_PER_RECORD`，界面也这么标。参考文档把「20min/人/天、14.4 万/年」当结论写；我们把假设写在数字旁边，这是加分项，别为了好看抹掉。]

#### 2.9 提升点（照抄参考文档的诚实姿态，不要删）
1. **用户画像 / 设备预警目前是规则引擎，不是模型**——界面和群卡片上都写着「由 规则引擎 生成」；`ProfileInsightProvider` 这个接缝就是留给 aily 技能的，换实现是改一处绑定。
2. **演示数据集的时间轴与多数打标是合成的**——企业周报只给日期不给时刻，且是半年前的数据，直接展示会变成「3612/3628 全部超时」这种无意义画面。合成规则、备份与还原见 README；合成记录一律盖 `打标来源 = demo-seed`，**真实 aily 打标的 19 条整条保留**。
3. **打标吞吐受 aily 单条 23 秒限制**，全量重跑不现实；Cron 每日分片是折中。
4. **Cron 自愈链路已实现并有单测，但尚未在生产观测到一次完整执行**（见场景 1 异常分支的注）。

## 2. 场景剧本

> **场景 0 是模拟的，场景 1–4 是真跑的。** 这条界线在文档和口播里都不能糊。
> 每个场景固定五段：**触发 → 系统做了什么 → 人做了什么 → 产出 → 覆盖能力**。

### 场景 0｜愿景全景（展厅四个视角 · 模拟）

用户端 AI 预诊与自助 → 自助失败转客服建单 → 工程师带着诊断和配件线索上门 → 后台把这次服务沉淀成改善项。四个角色共享同一份案例状态，任一角色重置会恢复整条流程。

⚠️ **这一层是确定性演示，不接真实 IoT / 知识库 / 工单系统。** 它回答「这套东西长大以后什么样」，写在方案介绍里，**不要和场景 1–4 混着讲**。

---

### 场景 1｜一条差评，从进来到闭环（含 AI 失败分支）—— 主干

| | |
|---|---|
| **触发** | 一条 400 客服渠道的差评落进多维表格（状态 `待分析`） |
| **系统做了什么** | ① aily 技能打标：情绪极性=差评、问题维度、AI 摘要、两套回复话术；② `triage()` **规则**判定：差评 → 建单，维度数决定严重度；③ 按「渠道+品类」路由到负责人，解析不到落兜底；④ 状态一次写到 `待跟进`，工单卡推到负责人单聊 |
| **人做了什么** | 飞书里点「开始跟进」→ 处理 → 「提交跟进结果」（填跟进记录）→ 「确认闭环」（填闭环结论） |
| **产出** | 状态到 `已闭环`、闭环时长入库；看板的已建单 / 已闭环 / 闭环率随之变化 |

**异常分支：AI 挂了怎么办**（参考文档完全没有这一层）

| | |
|---|---|
| **触发** | aily 超时、网关 504、或输出不合契约 |
| **系统做了什么** | 状态落 `分析失败`，写入失败原因与原始输出，重试次数 +1——**失败是一等状态，不是静默丢弃** |
| **自愈** | 次日 Cron 分片作业自动重取 `分析失败`，重试次数到上限即停止重取（不会无限重试） |
| **人工兜底** | 「分析异常」队列（当前 20 条）里打开一条，点「立即分析」当场重跑 |

**覆盖能力**：落库 → AI 打标（双轨契约）→ 规则 triage → 负责人路由含兜底 → 卡片三重校验 → 状态机幂等 → 闭环时长统计 → 失败可见 / 重试上限 / Cron 自愈 / 人工介入

**要讲的点**：AI 不决定业务。同一条记录换个模型，摘要会变，**建不建单不会变**——那是 `triage()` 里的规则。
⚠️ 注：Cron 自愈已实现且有单测，但**生产尚未观测到一次完整执行**；不要写「已在生产每日运行」。

### 场景 2｜高严重度：升级提请 → 拉群协同 → 闭环纪要

| | |
|---|---|
| **触发** | 打标结果为差评且命中 ≥2 个问题维度 → `triage()` 判严重度 **高** |
| **系统做了什么** | 推进到 `待跟进` 的同时，自动向兜底人推**升级提请卡片**——不是直接建群，建群要打扰一屋子人，得有人点头 |
| **人做了什么** | 兜底人点「确认拉群」或「暂不需要」 |
| **系统接着做** | 建群 → 工单卡发进群 → 群 ID 回写记录（**同一条工单只提请一次**：已建群 / 已拒绝都不再打扰）；群内 @机器人 基于 Base 事实问答；闭环时产出群聊纪要 |
| **产出** | 一个带上下文的协同群，而不是一句「大家看下这个」 |

**覆盖能力**：严重度判定、升级幂等、拉群、群内事实问答、闭环纪要
**要讲的点**：升级是**提请**不是自动执行——系统判断该升级，拉不拉群由人点头，这条边界写在设计里。

### 场景 3｜派工上门：工程师不用打开后台

| | |
|---|---|
| **触发** | 一条 `待跟进` 的工单需要有人上门 |
| **人做了什么** | 客服（或管理员）在工单详情页「上门」里选一个工程师 → 派工 |
| **系统做了什么** | ① 校验：只有负责人或管理员能派，只能派给人员管理里的**工程师**；② 写 `上门工程师` + `派工时间`（多维表格与镜像各一份）；③ 给工程师飞书推**上门任务卡**：机型 / 设备标识 / 用户原话 / AI 摘要与维度 / 严重度 / **这台设备一共几条反馈、几条未闭环** / 复发判断与上门前建议（标注规则引擎）/ 派单人 |
| **工程师做了什么** | 在飞书卡片上点「已到场，开始处理」→ 工单进 `跟进中`；处理完点「回填处理结果」填写现场做了什么 → 工单进 `待闭环` |
| **产出** | 工单回到客服手里确认闭环；现场记录进了跟进记录，而不是散在微信里 |

**覆盖能力**：角色模型（客服/工程师/管理员）、派工鉴权、真实卡片下发、工程师侧状态流转、权限边界（不给工程师「确认闭环」）

**要讲的点**：这一段回答命题里那句「多次上门、多次描述、反复等待」——**上门的人第一次知道这台机器之前发生过什么**。边界也说清：没有真实配件库与派单系统，卡上的「上门前建议」是规则引擎产出。

### 场景 4｜标识维度预警：这个用户在升级 / 这台设备在复发

同一套机制的两个面：把散落的记录按**人**和按**机器**聚起来，让模式先于抱怨被看见。

| | 用户侧 `U-81D8FA28` | 设备侧 `D-BE66CB3A` |
|---|---|---|
| **系统看到什么** | 7 条反馈**全在 21 小时内**、差评 4、「维修技术」重复、平均正文 445 字、有夜间反馈 | 7 次报修**全在 24 小时内**、同一维度「维修技术」重复、含高严重度 |
| **判定** | 关注度 **高**：`强烈不满 / 陈述详尽 / 连续追问 / 夜间反馈 / 易升级 / 多点关注`，结论「短时间内连续 7 次反馈，情绪正在升级」 | 预警 **高 / 疑似维修未彻底**，结论「7 次报修且集中在维修技术，建议按复发处理」 |
| **建议动作** | 优先电话回访（不要只回文字）；按「维修技术」指派对口工程师，避免重复上门 | 升级为整机更换 / 换件评估；拉群会同产品与售后；指派资深工程师复核上次维修 |
| **人做了什么** | 照建议动作走 | 点「拉群处理」→ 建群、**分析卡片作为群里第一条消息**、该设备未闭环工单的负责人一起拉进来 |

**覆盖能力**：用户/设备维度聚合、情绪升级判定、复发判定、标识级拉群（幂等落在 Postgres）、群卡片
**要讲的点**：每条「依据」都能对着下面那张记录表逐条核对——这是它敢在评委面前展示的原因。

⚠️ **设备侧不是 IoT 信号。** 我们没有设备遥测，`设备标识` 是从 VOC 记录重建的。讲的是**「同一台机器的重复报修被系统先看见」**，别说成「设备上报了异常」。真 IoT 版本只在场景 0（模拟）。

### 场景 5｜运营的一天：队列 → 筛选 → 同源串联 → 看板洞察

| | |
|---|---|
| **早上分流** | 待处理 226 / 超时风险 139 / 未分配 13 / 分析异常 20。按停留时长排序先处理最久的；未分配的直接「我来跟进」认领；换人走「改派」（通讯录解析，不是手填名字） |
| **查一件事** | 九个筛选叠加（冰箱 + 差评 + 维修时间）；搜机型、搜 400 工单号、搜用户标识。**粘个链接给同事，他打开就是同一屏**（列表状态全在 URL 里） |
| **一次服务的完整声音** | 详情页「另有 6 条同来源单号」→ 一键筛出。3629 行只有 2773 个不同来源单号，**约 856 行与别人共用同一个来源工单**——同一次服务在不同渠道留下的声音被串起来，不会被当成 7 个独立问题 |
| **月底复盘** | 数据概览：问题维度头三名 **维修价格 196 / 维修技术 182 / 环境设施 138** → 按维度筛出记录 → 输出洞察 |
| **改路由** | 人员管理：三列的路由表（负责范围 / 负责人 / 兜底）就在工作台里改，写回的还是流水线读的那张表。范围从数据里真实出现过的渠道与品类**选**出来——精确匹配意味着打错一个字符的规则永远不命中，且没有任何地方会报错。重复范围、第二个兜底、删掉唯一兜底都会被当场拒绝并说明后果 |

**覆盖能力**：五队列、九筛选、全文搜索、四排序、分页、URL 即状态、认领 / 改派、派工、上游溯源与同源串联、聚合看板、角色与路由配置

### 现场演示的起点：新建工单 / 设置里的两个触发器

**设置（左下角）→ 开发者选项**：`生成演示工单`（建一条 `待分析` 真工单并落到详情页）、`触发设备异常预警`（挑当前复发最严重的设备推预警卡 + 站内消息，并打开该设备页）。


**工单列表右上角「新建工单」**：选渠道、选品类、写机型、把用户的话原样贴进去（可选填用户/设备标识）→ 建出一条 `待分析` 的真工单并直接跳到它的详情页 → 点「立即分析」，后面整条链路都是生产链路：打标 → triage → 建单 → 路由到客服负责人 → 工单卡进飞书 → 站内消息 → 派工 → 回填 → 闭环。

- **可以用评委现场说的话**当输入，比拍现成记录更有说服力；
- **不消耗库存**：不用再花掉一条 `待分析` 记录；
- 渠道/品类只能从数据里已有的取值里选（这两列是单选，写个新值会在企业表里凭空多一个选项）；
- 每条这样建出来的记录都盖着 `来源明细 = 手动录入（演示）`，事后在多维表格里一筛就能找出来清掉。

⚠️ 目前**没有做删除按钮**——要清理就在多维表格里按 `来源明细` 筛出来删。

### 拍摄前后：一条命令把素材摆好 / 还原

**问题**：每个镜头都会**吃掉**它演示的状态——`立即分析` 拍完那条就不再是 `待分析`，第二条就没得点了；流转拍完那条已闭环。重拍一次就消耗一条记录，数据集也会慢慢偏离文档里写的形状。

**`POST /api/voc/demo/rehearsal`**（需登录，三个动作）：

```bash
# 看会选中哪几条，什么都不写
curl -X POST -b "$COOKIE" https://onecare.ohmyfeishu.top/api/voc/demo/rehearsal

# 存快照并布置（把三条摆回起始状态）
curl -X POST -b "$COOKIE" 'https://onecare.ohmyfeishu.top/api/voc/demo/rehearsal?do=prepare'

# 拍完还原
curl -X POST -b "$COOKIE" 'https://onecare.ohmyfeishu.top/api/voc/demo/rehearsal?do=restore'
```

返回里直接给**每个镜头用哪条记录 + 打开哪个页面**（`shot` / `recordNumber` / `href`），照着开就行。

它做了什么、更重要的是**不做什么**：

- 只在状态机允许的范围内挪记录，**不伪造记录**；
- **绝不碰那 19 条真实 aily 打标**（它们是数据集里唯一的真模型产出，摆素材不能拿它们开刀）；
- **不把已闭环的工单拖回未闭环**——那是状态机产生不出来的状态，演示里也不该出现；
- 快照是先存后改：还原放回的是**当时真实的样子**，不是猜一个「干净」状态；
- 两个库一起写（Postgres 镜像 + 多维表格），否则网页和飞书卡片会在录制中显示成两个状态；
- ⚠️ **删不掉已经建出来的飞书群**——建群是对外的、不可撤销的。还原只是让记录不再指向它，群还在大家的侧边栏里。每次 restore 的返回里都会重复这句。

实测一次完整往返（prepare → 模拟拍摄把工单跑到已闭环 → restore）：镜像与多维表格都回到 `待跟进`，负责人与建单时间原样保留。

### 数据口径的一处订正（2026-08-15）

导入时有 **225 条 400 客服工单**的 `记录编号` 是被 Excel 写成科学计数法的一串数字（`2.0148551742220401E+18`）——不是我们生成的，是导出文件里就长这样。已统一改成与其余记录一致的 UUID；**真实的 400 工单号在 `来源单号` 里原样保留**（这 225 条全部有值），这 225 条也都没有协同群，所以没有任何可追溯的信息因此丢失。顺带修掉的 bug：编号里的 `+` 在链接里会被转义，参数到页面时没有解码，导致这 225 条点进去全部显示「工单不存在」。

### 拍摄注意

1. **登录态**：用飞书客户端走 `/enter` 进，别用本地 mock session 出镜。
2. **同一条别重复用**：S3 拍完那条就不再是 `待分析` 了；S9 拍完那条也不再是 `分析失败`。当前库存：待分析 498、分析失败 20（重试次数均为 0，都还能重试）。
3. **S6 不再受升级时机限制**：每条工单详情页都有「拉群处理」，随手一条就能拍。升级卡片那条链路（打标那一刻自动推提请卡）仍然只在打标时触发，要拍**自动升级**的版本才需要挑一条原文明显是严重投诉的 `待分析` 记录去跑。
4. **群会真的建、卡会真的发**：S6 / S7 会在同事飞书里生成真实群聊并拉人；S12 的派工会给张睿哲发一张真实的上门任务卡。先打招呼，或约定用哪条工单拍。
5. **诚实边界**（口播和字幕都别越线）：画像/设备预警说「规则引擎」不说 AI；演示数据的时间轴与多数打标是合成的，要展示真实 AI 产出就开 S14；超时 SLA 72 小时和人工 5 分钟/条都是假设值。
