# OneCare 多页面展示站主页设计

## 状态

用户于 2026-07-17 确认把 OneCare 从单一展示页逐步扩展为多页面 MVP，并要求先完成主页。后续将分别建设用户、客服、工程师和后台视角，其中用户视角计划包含一个简单的 AI 聊天智能体演示。

本规格只定义并交付主页。四个角色页面、真实 AI 对话、真实业务数据、后台接口和系统集成不属于本阶段。

## 目标

把主页建设为 OneCare 多页面方案的统一入口，让比赛评审在一次连续浏览中理解：

1. OneCare 要解决什么用户服务问题；
2. 用户、客服、工程师和后台四个角色将如何参与同一条服务闭环；
3. “感知—诊断—编排—服务—学习”五层架构如何把信号转化为结果；
4. 一个典型服务问题如何贯穿五层方案；
5. 三位参赛成员如何形成互补能力。

主页同时建立后续角色页面必须复用的品牌、布局、组件和动效基线。它不是实际业务控制台，不得把静态案例或目标指标描述为真实运行数据。

## 用户与浏览场景

主页的第一受众是比赛评审和方案决策者，第二受众是未来参与服务流程的业务角色。典型浏览路径是：

1. 从首屏理解核心主张；
2. 预览四个角色入口及各自价值；
3. 理解五层架构；
4. 通过一个完整案例理解方案如何工作；
5. 查看团队能力与原型边界；
6. 已登录用户可以继续进入现有受保护工作台。

## 多页面信息架构

长期路由规划如下：

- `/`：本阶段实现的方案主页；
- `/experience/user`：用户视角，后续包含 AI 聊天智能体演示；
- `/experience/support`：客服视角；
- `/experience/engineer`：工程师视角；
- `/experience/operations`：后台视角；
- `/dashboard`：保留现有飞书登录后的受保护静态工作台。

本阶段不创建四个 `/experience/*` 页面，也不在主页放置会产生 404 的链接。角色入口以可识别的预览卡呈现，并统一标记“下一阶段开放”。后续角色页面上线时，卡片在不改变视觉结构的前提下升级为链接。

主页顶部导航只链接当前页面已经存在的锚点：角色视角、五层架构、方案路径和团队。现有飞书登录或进入工作台入口继续保留。

## 主页结构

### 1. 全局页头

页头使用 OneCare 品牌，不在网页名称中出现 Hisense。页头包含：

- OneCare 字标；
- 当前页面的四个锚点导航；
- 根据会话状态显示“飞书登录”或“进入工作台”；
- 移动端在品牌与登录入口下方显示可横向滚动的锚点导航，不引入菜单开关状态。

页头应成为后续所有公开角色页面的共享组件。认证 URL、会话读取和退出行为不在本阶段修改。

### 2. 首屏主张

保留当前“让每一次服务，都比问题更早一步”的核心标题，以及现有轨道、脉冲和分层渐入动效。首屏正文明确 OneCare 面向海信智能家庭场景，但 OneCare 字标、页面标题和 URL 不出现 Hisense。

首屏的主要操作是查看方案，滚动到角色视角；次要操作是飞书登录或进入工作台。原型边界用简短状态标签表达，不用长段免责声明打断首屏。

### 3. 四个角色视角预览

该区域是多页面产品的入口地图，以四张视觉一致的角色卡展示：

| 角色 | 核心任务 | 后续页面重点 | 本阶段状态 |
| --- | --- | --- | --- |
| 用户 | 描述问题、获得即时帮助、跟踪进度 | AI 聊天、主动提醒、预约与评价 | 下一阶段开放 |
| 客服 | 理解诉求、补齐上下文、快速分流 | AI 摘要、知识建议、智能路由 | 下一阶段开放 |
| 工程师 | 一次上门前获得正确诊断线索 | 设备预诊、配件建议、任务反馈 | 下一阶段开放 |
| 后台 | 监控服务质量并推动持续改善 | VOC 趋势、异常预警、闭环治理 | 下一阶段开放 |

每张卡使用同一结构：编号、角色名、一句话价值、三项能力标签、状态和方向性箭头。卡片本阶段不是交互控件，不进入键盘焦点，也不可导航到不存在的页面；悬停只提供视觉反馈。升级为真实链接后再提供键盘焦点样式。

### 4. 五层架构

架构区域使用连续的五段信号链，而不是五张彼此独立的普通卡片：

| 层 | 输入 | AI 与系统动作 | 输出 |
| --- | --- | --- | --- |
| 感知 | IoT 设备信号、用户声音、服务记录 | 统一采集并识别异常与意图 | 可处理的问题信号 |
| 诊断 | 问题信号、历史案例、设备知识 | 风险判断、原因推断、置信度评估 | 诊断建议与信息缺口 |
| 编排 | 诊断建议、人员、配件、时效规则 | 任务拆解、角色路由、资源匹配 | 可执行的服务计划 |
| 服务 | 服务计划、用户偏好、现场反馈 | 智能客服辅助、工程师执行、进度同步 | 解决结果与用户确认 |
| 学习 | 处理结果、回访、满意度、VOC | 效果评估、知识沉淀、问题聚类 | 下一轮预诊与产品改善 |

桌面端横向展示；窄屏改为纵向时间轴。信号线按“感知 → 学习”方向缓慢流动，悬停某一层时突出当前节点及其输入输出。这里展示的是方案架构，不宣称数据管道或 AI 模型已经接入。

### 5. 方案路径

使用“冰箱温控异常”作为一个贯穿五层的静态案例：

1. 感知：设备温度波动与用户历史反馈形成异常信号；
2. 诊断：AI 给出传感器或风道相关的预诊建议，并标注待确认信息；
3. 编排：系统匹配工程师、建议配件和可预约时间；
4. 服务：用户收到连续进度，工程师带着上下文上门并记录结果；
5. 学习：回访结果进入 VOC 聚类，更新案例知识与产品改善线索。

案例中的内容必须统一标记为“方案演示”。不展示伪造的真实用户姓名、设备序列号、精确成功率或生产环境指标。

### 6. 团队能力

在未获得真实成员信息前，使用明确占位，不虚构姓名、履历、公司、院校、奖项或项目经验：

- 成员 01：产品策略与业务洞察；能力标签为“业务建模 / 用户研究 / 方案规划”；
- 成员 02：AI 工程与系统架构；能力标签为“AI 应用 / 系统设计 / 工程实现”；
- 成员 03：体验设计与服务创新；能力标签为“服务设计 / 交互原型 / 视觉表达”。

每张成员卡包含角色方向、三项通用能力标签和“成员信息待补充”状态。真实资料到位后只替换内容数据，不改变卡片组件。

### 7. 页尾与边界

页尾包含 OneCare、方案年份、当前原型边界和页面锚点。必须明确：主页是方案展示；IoT、VOC、客服、工单、配件、回访与 AI 服务尚未真实接入。

## 共享组件与复用约束

后续页面不得各自复制一套页头、页尾、颜色和卡片。实现阶段应建立以下共享边界：

- `SiteHeader`：公开页面统一导航、品牌与登录入口；
- `SiteFooter`：统一边界说明和页尾导航；
- `PageIntro`：角色页标题、说明、状态和首要操作；
- `SectionFrame`：章节编号、眉题、标题和内容宽度；
- `StatusTag`：方案演示、下一阶段开放、身份状态等标签；
- `RoleCard`：主页角色入口，后续可无结构变化地升级为链接；
- `SignalFlow`：五层架构与后续角色页共用的流程节点视觉；
- CSS 设计令牌：颜色、字体、间距、边框、阴影、动效曲线和断点。

主页专用章节可以组合共享组件，但不应把整个主页写成一个超大组件。静态业务内容与 JSX 结构分离为带只读 TypeScript 类型的数据，使后续页面可以复用角色名称、能力标签和五层定义，避免文案漂移。

## 视觉方向

视觉参考海信美国官网当前的高对比黑白、青绿色品牌强调和产品式大面积留白，但不复制其页面布局、图片或品牌资产。OneCare 保持独立字标。

建议设计令牌：

- 主墨色：`#0B0D0C`；
- 纸白：`#F5F7F5`；
- 海信参考青绿：`#00A4A0`；
- 浅青背景：`#DDF3F1`；
- 中性文字：`#626A67`；
- 分隔线：墨色 16% 透明度。

主页完全移除当前橙色主强调和酸性黄，以免与青绿色品牌方向竞争。旧工作台本阶段不修改，暂时保留原有颜色，直到工作台进入单独的视觉统一阶段。

排版保持现有中文宋体标题与窄体英文技术标签的组合。大标题、细边框、非对称留白和技术编号继续构成 OneCare 的编辑式工业气质。

## 动效与交互

保留并统一当前动效：

- 首屏轨道脉冲；
- 标题、正文和操作的分层进入；
- 卡片悬停反色或青绿高亮；
- 扫描线与信号流动；
- 页面内锚点平滑滚动。

新增动效只服务于信息关系：五层信号沿路径流动，角色卡在悬停时显示未来入口意图；它们升级为真实链接后才增加键盘聚焦反馈。不得加入影响阅读的持续大幅位移、随机粒子或重度 3D。

所有动效遵循 `prefers-reduced-motion`。禁用动效后，内容、状态和层级仍完整可见。

## 响应式与无障碍

- 桌面端维持宽幅编辑式布局；
- 平板端四角色卡采用两列；
- 手机端角色卡单列，五层架构改为纵向时间轴；
- 锚点导航和 CTA 具备可见键盘焦点；本阶段非交互的角色卡不进入键盘顺序；
- 颜色对比满足 WCAG AA 的正文可读性；
- 纯装饰轨道、扫描线和信号节点不进入无障碍树；
- 标题层级按页面结构连续，不用视觉字号替代语义标题。

## 技术边界

- 继续使用现有 Next.js App Router、React、TypeScript 和 CSS，不新增 UI 框架；
- 只有需要状态的导航或交互单元才使用 Client Component；
- 首页静态章节默认保持 Server Component 友好；
- 不修改飞书 OAuth、Cookie、会话、认证 Route Handlers 或生产环境变量；
- 不新增数据库、AI SDK、聊天接口、队列或外部业务系统；
- 不创建无法完成的角色页面，也不使用死链模拟完成度。

## Preview 交付

主页分支完成本地验证后，发布到当前已链接的 OneCare Vercel 项目，生成非 Production 的 Preview URL 供用户确认。若 Preview 受 Vercel Deployment Protection 保护，则为本次评审窗口生成限时 Shareable Link，但不得把分享绕过值写入仓库。验收 Preview 时必须验证 HTTP 200，并检查“四个视角”或“五层架构”等本次独有文案。

本阶段不修改 Production 部署、稳定生产域名、飞书回调或环境变量。由于 Vercel Preview 环境未配置飞书认证变量，Preview 只用于主页视觉和内容确认；预览域名上的飞书登录不属于本阶段验收范围。

仓库 harness 记录用户的持续授权：今后完成的分支只要包含用户可见的网站内容修改，就在本地验证后自动创建 Vercel Preview，并在保护开启时创建限时分享链接，把可直接评审的 URL 交给用户确认。该持续授权不扩展到 Production、生产密钥、飞书回调、GitHub 推送、PR 或合并。

## 测试与验收

实现必须按 RED → GREEN → REFACTOR：

1. 先更新主页展示测试，断言四个角色、五层架构、方案案例、团队占位和原型边界；
2. 测试必须先因主页内容缺失而失败；
3. 实现最小的共享组件与主页章节后使测试通过；
4. 补充移动导航或交互组件的键盘与状态测试；
5. 保持现有认证和工作台测试通过；
6. 运行 `npm test`、`npm run lint`、`npm run typecheck`、`npm run build` 和 `git diff --check`。

验收时还需人工确认：

- 首页不存在指向未实现 `/experience/*` 路由的死链；
- OneCare 标题和 URL 不出现 Hisense，正文可以出现海信；
- 四角色页面的未来入口清晰但不冒充已完成；
- 五层架构在桌面和手机尺寸都能按正确顺序阅读；
- 三位成员全部是明确占位；
- 关闭动画后页面仍可完整理解；
- 现有飞书登录和受保护工作台入口保持可用。

## 后续阶段

主页完成后，优先为 `/experience/user` 单独编写规格。该规格将定义 AI 聊天演示的对话范围、模型或静态模拟边界、数据安全、失败状态，以及如何复用本规格中的页面壳、状态标签、流程节点和设计令牌。
