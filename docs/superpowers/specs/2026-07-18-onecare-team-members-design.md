# 万护 OneCare 团队成员页内容设计

## 目标

把团队页现有的三张能力占位卡替换为张禹健、张睿哲和黄齐的真实成员简介。页面应让比赛评审快速看出三人的学历背景、代表经历与能力互补关系，同时保持万护 OneCare 当前黑白品牌展厅视觉。

## 信息来源

成员信息仅来自用户提供的三份单页简历：

- `南京大学_软件工程_硕士_张禹健.pdf`；
- `张睿哲简历.pdf`；
- `黄齐_简历CN.pdf`。

本次不从公开网络补充或推断履历。页面不展示简历中的照片、电话、邮箱、社交账号、政治面貌、民族或其他与团队能力无关的个人信息。

## 采用方案

采用“角色导向的精简成员卡”：每张卡按姓名、角色定位、学历、两条代表经历、能力关键词的顺序展示。该方案保留足够的履历证据，又不会把团队页变成密集的简历列表。

不采用以下方案：

- 简历式罗列：信息更完整，但会破坏整屏团队页的浏览节奏，且弱化三人的能力互补关系；
- 极简署名：只显示姓名、角色和标签，视觉更轻，但缺少学历与代表成果支撑。

## 页面结构与视觉

- 保留现有 `#team` 一级页面、`03 · 团队` 标题和黑色页尾，不新增路由或导航入口；
- 页面标题继续使用“三种能力，共同完成服务创新”；
- 导语改为说明团队覆盖 AI 工程、安全仿真和业务产品化，不再出现“成员信息待补充”；
- 桌面端保持三列圆角白卡，移动端堆叠为单列；
- 卡片不显示照片，也不创建头像或照片占位框；
- 姓名作为卡片最高视觉层级，角色定位作为次级标题；
- 学历单独成组，明确区分“硕士研究生”与“本科”；
- 两条代表经历使用短段落或列表，关键词保持简洁，不使用密集徽章墙；
- 继续遵守现有 MiSans、白色主体、圆角卡片、青绿色强调和响应式规则。

## 数据与组件边界

扩展 `TeamMember` 只读内容模型，使其包含：

- `index`；
- `name`；
- `role`；
- `education`；
- `highlights`；
- `capabilities`。

`teamMembers` 继续作为团队内容的唯一数据源。`LandingContent` 只负责语义化渲染，不在组件内硬编码成员履历。此次不引入头像资源、外部请求、CMS、数据库或新的客户端状态。

## 可访问性与隐私

- 每位成员使用独立 `article`；
- 学历和代表经历具有可读的小标题或列表语义；
- 不依赖颜色区分姓名、角色、学历和经历；
- 缩放到 200% 或在窄屏堆叠时，文字不得裁切或横向溢出；
- 不把三份简历复制进仓库，也不把联系方式等个人信息写入页面、测试或文档正文。

## 测试与验收

按 RED → GREEN → REFACTOR 实施：

1. 先更新 `app/landing-content.test.tsx`，断言三位姓名、角色定位和六条学历信息出现，并确认旧占位文案消失；
2. 运行目标测试并确认它因新内容尚未实现而失败；
3. 扩展 `TeamMember` 数据并更新团队卡片语义结构；
4. 调整团队卡片样式，确保三列和移动端单列均能容纳新增信息；
5. 运行目标测试、完整测试、Lint、类型检查、生产构建和 `git diff --check`；
6. 在桌面与移动端检查团队页，不出现照片、裁切、溢出或难以扫描的密集文本；
7. 因团队页属于用户可见网站内容，完成本地验证后发布非 Production Vercel Preview，并验证 HTTP 200 与三位姓名标记。
