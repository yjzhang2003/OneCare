# VOC 协同群与群内智能体设计（2026-08-12）

## 1. 背景与目标

VOC 闭环目前的协同形态是**单聊**：分片作业给负责人推一张工单卡，他一个人点四个按钮把状态推到闭环。这对中低严重度够用，但高严重度的投诉往往需要多方在场——负责人、能拍板的管理、可能还有客服和工程师——而单聊里没有"在场"这回事。

本设计新增一条**升级路径**：高严重度工单由机器人主动提请拉群，人工确认后建群、拉人、在群内发工单卡；群里 `@机器人` 可以就这条工单自由提问，答案由 aily 技能生成、事实由 Bitable 提供；闭环时把群内过程收敛成一段结论写回 Base。

不变的部分：状态写入仍然只发生在卡片回调里，身份仍然来自签名事件的 `event.operator.open_id`，三重校验（记录存在、操作者是负责人、状态转移合法）一个字不改。

aily 平台的两条硬约束（2026-08-11 实测，本设计的新技能同样受其约束）：

- 技能自定义参数**只支持 String / Boolean / Float / Integer**，没有数组与对象。复杂入参必须序列化成 String 传，由工作流内部解析。
- `data.output` 外面套了一层技能响应参数的信封：`{"output":"<真实载荷>"}`。`unwrapSkillOutput()` 已处理。

## 3. 触发与人工闸门

### 3.1 何时提请拉群

分片作业把一条记录推进到 `待跟进`（即 triage 判定要建单）时，若该记录 `严重度 = 高`，机器人向**兜底人**发送一张**升级卡**。

兜底人取自 `负责人表` 中勾选了兜底的行。取不到兜底人时不发升级卡，也不报错——记录照常进入 `待跟进`，走原有单聊派单路径。理由：拉群是增强，不是闭环的必要条件，缺一个配置项不该让主流程失败。

严重度为 `中` / `低` 的记录行为完全不变。

### 3.2 升级卡

内容：记录编号、渠道/品类、严重度、情绪极性、问题维度、AI 摘要、负责人姓名。**不含用户原文**——升级卡是通知，原文进群后再给，减少一次不必要的传播面。

两个按钮：

| action | 语义 |
| --- | --- |
| `voc_open_war_room` | 建群协同 |
| `voc_decline_war_room` | 暂不需要 |

两个 action 加入 `VOC_CARD_ACTIONS` 白名单（`src/features/feishu-bot/card-types.ts`），沿用现有三重校验，其中「操作者是负责人」这一条对这两个动作放宽为「操作者是负责人**或**兜底人」——批准升级本就是兜底人的职权。

兜底人身份的解析方式：读 `负责人表`（已有 `listOwnerRules`），取所有 `兜底 = true` 行的 `负责人` open_id 构成集合。放宽只对这两个 action 生效；四个状态动作的负责人校验一个字不改，因为改状态是负责人的职权，不是批准人的。

发送升级卡复用分片作业既有的出站路径（`app/api/voc/analyze/route.ts` 的 `notifyOwner` 依赖，底层是 `sendFeishuMessage` 按 open_id 发单聊）。发送失败按现有 `notifyErrors` 计数，不阻塞状态推进。

「暂不需要」把 `协同群 ID` 列写成常量 `declined`，据此不再重复提请。这个值同时是幂等标记：见 §4.2。

## 4. 建群

### 4.1 群的形态

- 群名：`VOC-{记录编号后 6 位}-{产品品类}-{严重度}`。记录编号是企业源文件的 uuid，取后 6 位既可辨识又不至于把群名撑爆；品类为空时该段省略。
- 成员：该工单的负责人（全部，`ownerOpenIds`）+ 点击按钮的操作者 + 机器人自身。去重后建群，因为操作者常常就是负责人之一。
- 负责人为空时照样建群，群里只有操作者和机器人。这不是错误状态：一条没有负责人的高严重度工单本来就该有人进来看，把建群卡在"必须先有负责人"上只会让最需要协同的那条工单进不了群。
- 群主：机器人。
- 建群接口：`POST im/v1/chats`，成员用 `user_id_list`（open_id）。

### 4.2 幂等

建群前先读该记录的 `协同群 ID`：

- 值形如 `oc_*` → 群已存在，不建，回 toast「协同群已存在」并附群名
- 值为 `declined` → 已被拒绝过，回 toast「此前已选择暂不需要」，不重复建
- 空 → 建群，成功后**立刻**把 `chat_id` 写回该列

先建群再写列，中间失败会留下一个没有记录在案的群。这是可接受的：多一个空群比多一条指向不存在的群的记录好排查，而且下一次点击会因为列仍为空而重建，不会卡死。写列失败时在 toast 里明确告知「群已建但未记录，请重试」。

分片作业重跑与按钮连点都靠这一列收敛。

## 5. 群内开场简报

建群成功后立即向该群发送一条工单卡，复用现有 Card 2.0 外壳与构建器：

- 记录编号、反馈时间（固定 +08:00）、渠道 / 产品品类、机型
- 严重度、情绪极性、问题维度
- **完整用户原文**，不截断、不脱敏。群成员是被点名拉进来处理这条投诉的人，看不到原文就没法处理；这与公开面的克制不矛盾——门禁的意义正是让授权者看到真实内容。
- AI 摘要
- AI 回复话术（`【语气】正文` 逐段渲染）
- 四个既有状态按钮：`voc_start_follow_up` / `voc_submit_follow_up` / `voc_confirm_closure` / `voc_mark_no_action`

四个按钮的行为、校验、写回逻辑全部不改。它们此前只在单聊里出现过，本设计只是把同一张卡发到群里；`event.operator.open_id` 在群聊回调中同样可用，负责人校验因此仍然成立。

## 6. 群内自由问答

### 6.1 触发与流程

群内 `@机器人 <问题>` 抵达 `im.message.receive_v1`（`chat_type = group`）。处理顺序：

1. 从 `chat_id` 反查工单：按 `协同群 ID = chat_id` 搜 `VOC 记录表`。查不到就回「这个群没有关联工单」并结束——不猜、不泛泛而答。

   `BitableClient` 目前只有 `getRecord` / `listRecords` / `updateRecord`，**没有按字段查询的方法**，本设计需要新增一个。用 `POST records/search` 带 `filter` 条件，而不是 `listRecords` 全表扫描：表里有 3628 条记录，全扫是 8 次分页请求，每条群消息都这么来一遍既慢又浪费跨境调用。新方法只做这一件事——按 `协同群 ID` 精确匹配返回至多一条记录。
2. 读该工单全量字段。
3. 取两个聚合事实：
   - 同 `问题维度` 近 7 天的记录数，及其中 `已闭环` 数
   - 同 `机型` 的记录数（机型为空则跳过该项）
4. 把工单事实、聚合事实、用户问题拼成技能入参，调 **问答技能**（§6.2）。
5. 回答以文本消息发回该群。

三秒响应要求：抵达事件后立即返回 200，实际回复走 `after()`，与现有事件处理一致。

### 6.2 问答技能契约

aily 上的**第二个**技能，打标技能 `skill_be790a868404` 不动。

入参（均为 String，因为 aily 自定义参数只支持标量）：

| 参数 | 内容 |
| --- | --- |
| `question` | 用户在群里问的原话，已剔除 `@机器人` 部分 |
| `facts` | JSON 字符串，含 `ticket`（工单全量字段）与 `aggregates`（§6.1 第 3 步的两项） |

出参：一个 String，自然语言回答。**不要求 JSON**——这是给人读的散文，套 JSON 只会增加解析失败面。因此 `unwrapSkillOutput()` 之后直接把字符串当答案，不过 `parseTagPayload`。

提示词要求技能：只根据 `facts` 回答，事实里没有的就说不知道；不编造工单号、不编造数字；回答控制在 200 字内。

### 6.3 失败处理

技能超时（120 秒，与打标同）、返回非 `success`、或回答为空——群里回一句「暂时答不上来，可以稍后再问，或直接在多维表格里查这条记录」。不重试，不静默。

## 7. 闭环归档

群内点击 `voc_confirm_closure` 时，现有逻辑照常写 `流程状态 = 已闭环` 与 `闭环时间`。在此之上追加一步：

1. 拉取群内消息：`GET im/v1/messages?container_id_type=chat&container_id={chat_id}`（`获取群组中所有消息` 已开通）
2. 把消息文本与工单事实送进问答技能，`question` 固定为「请把这次协同过程收敛成一段闭环结论，说明问题、处理动作与结果」
3. 结论写入 `闭环结论` 列，并在群里公示

**这一步失败不影响闭环。** 状态与闭环时间照写，因为闭环是已经发生的事实；`闭环结论` 留空，群里说明「闭环已记录，结论生成失败」。把结论生成放在状态写入之后、且不参与事务，就是为了让这条性质成立。

## 8. 数据模型改动

`VOC 记录表` 新增一列：

| 列名 | 类型 | 说明 |
| --- | --- | --- |
| `协同群 ID` | 文本 | 建群后写入 `chat_id`（`oc_*`）；被拒绝时写入常量 `declined`；空表示尚未提请或提请后建群失败 |

`VOC_FIELD_NAMES` 增加对应键（`src/features/bitable/field-map.ts`），`VocRecord` 增加 `warRoomChatId: string`。`schema-guard.ts` 的字段名校验随之覆盖新列。

**不新增选择型字段**，因此不存在选项污染风险。

## 9. 运营前提

`负责人表` 当前 0 条记录，必须先填真人，否则升级卡无人可发、群无人可拉。表的真实字段是 `负责范围`（文本）、`负责人`（人员）、`兜底`（复选框）。

**`负责范围` 匹配的是渠道，不是品类。** `resolveOwner`（`src/features/voc/assignment.ts`）依次尝试 `渠道/品类` 与 `渠道` 两种字面量，都不中才走兜底。按品类填（如 `冰箱`）会一条都匹配不上，所有工单都落到兜底人身上——看起来"能跑"，实际上路由从未生效。

建议填三行，覆盖导入数据里实际存在的全部三个渠道（`400 客服 1573` / `社媒 1038` / `电商评价 1017`）：

| 负责范围 | 负责人 | 兜底 |
| --- | --- | --- |
| `400 客服` | zhangyujian | ✓ |
| `电商评价` | huangqi | |
| `社媒` | zhangruizhe | |

`负责人` 一栏在多维表格界面用人员选择器挑选，由多维表格完成姓名到 open_id 的解析（见 §2）。需要更细的粒度时再加 `400 客服/冰箱` 这样的行，它会优先于 `400 客服` 命中。

## 10. 测试

- **纯函数**：群名生成（品类为空、记录编号短于 6 位）、幂等判定（`oc_*` / `declined` / 空）、事实拼装、`@` 前缀剔除、聚合计算
- **路由处理器**：升级卡两个动作的三重校验（含"负责人或兜底人"这一放宽）、建群失败时不写列、写列失败时的 toast 文案
- **问答**：查不到工单、技能超时、技能返回空、正常回答四条路径
- **闭环归档**：结论生成失败时状态仍然写入——这条是本设计最容易被实现成"一起回滚"的地方，必须有测试钉住
- **不做**：对真实飞书租户建群的自动化测试。建群有副作用且不可幂等清理，验证靠一次人工端到端演练

## 11. 明确不做

## 12. 验收

1. `严重度 = 高` 的记录推进到 `待跟进` 时，兜底人收到升级卡，卡上无用户原文
2. 点「建群协同」→ 群被创建，群名含记录编号后 6 位，负责人与操作者在群内
3. `协同群 ID` 列写入了 `oc_*`
4. 再点一次同一张卡 → 不新建群，toast 提示已存在
5. 点「暂不需要」→ 列写入 `declined`，后续不再提请
6. 群内首条消息是工单卡，含完整原文与四个按钮
7. 群内点「开始跟进」→ 状态变 `跟进中`；非负责人点击被拒绝且不写入
8. 群内 `@机器人` 提问 → 收到基于该工单事实的回答
9. 在一个没有关联工单的群里 `@机器人` → 明确回复无关联工单
10. 群内点「确认闭环」→ 状态与闭环时间写入，`闭环结论` 有内容并在群内公示
11. 人为让问答技能失败 → 闭环状态仍然写入，结论列留空，群内说明
