# 万护 OneCare 工单详情整页设计

## 1. 状态与目标

本规格记录 2026-08-13 对登录后运营工作台工单详情体验的调整。

当前工单列表通过 `?ticket=<记录编号>` 打开一个 620px 宽的 Arco `Drawer`。抽屉承载可执行操作、工单字段、完整原文、AI 摘要和 AI 回复话术。该形态限制了内容宽度，也让后续增加更完整的工单信息层级变得困难。

本次改造将工单详情迁移到独立整页路由，并采用三栏控制台布局：左侧章节导航、中间主要内容、右侧状态与动作。目标是改善信息层级和处理效率，同时复用已有数据、动作与权限边界，不扩大 VOC 闭环的业务能力。

## 2. 范围

### 2.1 本次包含

- 新增登录成员专用的独立工单详情路由；
- 工单列表整行和记录编号均跳转到独立详情页；
- 详情页隐藏工作台的全局工单队列侧栏；
- 详情页使用三栏布局，并提供小屏响应式降级；
- 保留当前工单的全部已展示字段和可执行操作；
- 返回列表时恢复队列、筛选、搜索、排序和页码；
- 区分工单不存在与数据读取失败；
- 删除旧抽屉及 `ticket` 查询参数承担的详情状态；
- 更新相关测试、README、技术栈说明和实施计划。

### 2.2 本次不包含

- 新增处理时间线、附件、评论、协同群消息或审计日志；
- 新增或修改飞书多维表格字段；
- 新增按记录编号查询飞书多维表格的 API；
- 修改工单状态机、认领规则、负责人权限或写入接口；
- 修改 aily 打标、Cron、卡片回调或作战室流程；
- 生产部署、环境变量修改、飞书后台配置或远程 Git 操作。

## 3. 路由与访问控制

详情页路由为：

```text
/workbench/tickets/[recordNumber]
```

`recordNumber` 使用现有 `WorkbenchTicket.recordNumber`，并在生成链接时通过路径段编码。详情页读取现有 `readWorkbenchCached()` 数据，在服务端按完整记录编号精确匹配。本阶段不新增 Bitable 单条查询能力，因为现有客户端只能用内部 `recordId` 高效读取单条记录，而列表链接当前公开的是记录编号；复用同一工作台缓存能保持列表与详情读到一致的数据，并限制改造范围。

访问控制沿用 `/` 的成员门禁：

- 有有效网站会话的租户成员可以读取详情；
- 无有效会话时不查询 VOC 数据，也不泄露工单是否存在；
- 详情路由不接受客户端提供的租户信息；
- 详情页写操作继续调用既有 `POST /api/voc/tickets/[recordId]/action`，服务端仍是负责人身份与状态合法性的唯一权威。

## 4. 列表现场恢复

详情链接携带当前列表的受控查询参数，不使用任意 `returnTo` URL：

```text
/workbench/tickets/VOC-001?queue=overdue&severity=%E9%AB%98&page=2
```

允许携带的字段与现有 `WorkbenchQuery` 的列表状态一致：

- `queue`
- `channel`
- `category`
- `polarity`
- `dimension`
- `severity`
- `state`
- `owner`
- `search`
- `sort`
- `page`

详情页使用既有查询解析规则校验这些字段，再把有效字段拼回站内 `/`。未知字段和非法枚举值被忽略；页码沿用当前非负整数校验。返回地址永远是站内相对地址，因此不存在开放重定向。

旧 `ticket` 参数不再参与新链接生成，也不再控制列表详情状态。迁移后访问带旧 `?ticket=` 的列表 URL 时，列表照常显示并忽略该参数，不打开抽屉。

## 5. 信息架构

### 5.1 页面框架

详情页保留 OneCare 运营控制台的品牌与登录用户信息，但隐藏列表页的全局工单队列侧栏。页面顶部显示面包屑：

```text
服务运营 / VOC 工单 / <短记录编号>
```

主体采用三栏：

1. 左栏：返回列表与章节导航；
2. 中栏：工单的主要阅读内容；
3. 右栏：状态、责任、时效和处理动作。

第一版只呈现当前数据已经支持的内容，不制造空的未来模块。

### 5.2 左栏：章节导航

左栏包含：

- 返回工单列表；
- 工单概览；
- 用户反馈；
- AI 分析；
- 回复话术；
- 处理信息。

章节导航使用页面内锚点。点击只滚动当前详情页，不改变路由，也不触发重新读取数据。左栏可在桌面端保持可见，但不得覆盖主体或形成独立业务状态。

### 5.3 中栏：主要内容

中栏按以下顺序呈现：

1. **标题区**：完整记录编号、状态、严重度、渠道 / 品类和工单主题。当前数据没有独立标题字段，因此主题取 `ticket.summary.trim()`；摘要为空时改取 `ticket.content.trim()`；两者都为空时显示“未提供反馈内容”。显示时截取前 60 个 Unicode 字符并追加省略号；它只是页面标题，不写回数据。
2. **用户反馈**：完整反馈原文、反馈时间、机型。
3. **AI 分析**：AI 摘要、情绪极性、问题维度和严重度。缺失值明确显示 `—`。
4. **回复话术**：按现有 `tone + text` 结构展示全部 AI 回复草稿；没有草稿时显示 `—`。
5. **处理信息**：建单时间、闭环时间、闭环时长和协同群是否存在。协同群只显示已有事实，不新增跳转或群操作。

### 5.4 右栏：处理上下文

右栏包含两个区域：

- **当前处理**：流程状态、负责人、严重度、停留时长、超时标记以及 `WorkbenchActions`；
- **关键字段**：记录编号、渠道、品类、机型、反馈时间、建单时间和闭环时间。

右栏在桌面视口中保持在可见区域内，使操作人员阅读长原文时仍能看到状态和动作。继续明确提示：状态流转只有负责人本人能执行，其他人会被服务端拒绝；改派负责人仍在多维表格完成。

`availableActions(ticket)`、`canClaim = !ticket.hasOwner` 和 `WorkbenchActions` 原样复用。详情页不得复制状态机规则，也不得在客户端推断当前用户是否为负责人。

## 6. 响应式行为

- 宽屏：三栏同时显示；中栏占主要宽度，左右栏使用有限宽度；
- 中等宽度：左侧章节导航收敛为顶部横向锚点，正文与右栏保持双栏；
- 小屏：全部变为单栏，顺序为返回与章节导航、标题和状态、处理动作、主要内容、关键字段；
- 页面不得产生整体横向滚动；长记录编号、原文和回复话术允许换行；
- 处理动作在小屏进入正常文档流，不使用遮挡内容的固定底栏。

## 7. 数据流与更新行为

1. 服务端校验网站会话；
2. 服务端调用 `readWorkbenchCached()`；
3. 从 `data.tickets` 按完整 `recordNumber` 精确匹配；
4. 把单个 `WorkbenchTicket`、当前时间和经校验的列表返回地址传给详情展示组件；
5. 客户端动作岛继续向既有工单动作接口提交 `recordId` 与 `seenState`；
6. 写入成功后沿用现有 `router.refresh()`，重新读取已失效缓存并刷新详情页；
7. 写入冲突、非负责人、非法状态和其他错误继续由既有动作接口与 `WorkbenchActions` 展示，不在详情页另造一套错误协议。

列表页仍由服务端完成筛选、排序和分页。删除抽屉后，列表客户端不再需要接收或解析 `view.selected`；查询层可以移除 `WorkbenchPage.selected` 和 `WorkbenchQuery.ticket`，但不得改变其他查询行为。

## 8. 错误与空状态

### 8.1 工单不存在

当 VOC 数据读取成功，但没有匹配记录编号时，详情页显示：

- “工单不存在或已被移除”；
- 请求中的记录编号；
- “返回工单列表”操作。

该状态不提供写操作。

### 8.2 数据读取失败

当 `readWorkbenchCached()` 返回失败状态时，详情页显示：

- “工单暂时无法加载”；
- 不渲染任何工单字段或数字；
- “重试”操作；
- “返回工单列表”操作。

读取失败不得被表现为工单不存在。

### 8.3 未登录

未登录请求沿用现有授权入口与失败防循环规则。VOC 数据查询发生在会话确认之后，未登录页面不得根据记录编号返回不同文案。

## 9. 组件边界

组件边界固定如下；实施计划可以在不改变职责的前提下调整文件拆分：

- **详情路由页面**：会话校验、数据读取、记录定位和错误状态选择；
- **详情页面外壳**：运营品牌栏、面包屑和三栏响应式结构；
- **详情内容组件**：只负责展示 `WorkbenchTicket`；
- **章节导航**：接收固定章节定义并生成锚点；
- **动作区域**：复用 `WorkbenchActions`；
- **返回链接构造器**：从受控 `WorkbenchQuery` 生成详情链接和返回列表链接。

可复用的格式化逻辑（短记录编号、上海时间、停留时长和颜色映射）应从当前超大的 `app/workbench-console.tsx` 提取到聚焦的工作台展示模块，供列表和详情共同使用。只提取本次两处都需要的逻辑，不做无关重构。

## 11. 安全与产品边界

- 详情页不会把 `recordId` 用作公开显示标识，但动作提交仍在服务端内部使用它；
- 不把负责人 `open_id` 传到浏览器；
- 不信任客户端的状态、负责人或租户参数；
- 不开放任意返回 URL；
- 不把 AI 摘要或回复话术描述为人工确认事实；
- 不把假设 SLA 72 小时描述为合同约定；
- 不改变多维表格无 CAS 的既有限制，冲突仍由 `seenState` 尽力检测；
- 缺失租户上下文继续默认为无访问权限。

## 13. 验收标准

1. 登录成员从工单列表点击任意行后进入独立详情 URL，页面不出现侧拉抽屉；
2. 详情页桌面端呈现左侧章节导航、中间主要内容、右侧处理上下文；
3. 全局工单队列侧栏在详情页隐藏；
4. 五个章节均只使用当前已有真实字段或明确缺失值；
5. 状态动作、认领、权限拒绝和写后刷新与改造前一致；
6. 返回列表恢复进入详情前的队列、筛选、搜索、排序和页码；
7. 工单不存在、数据读取失败和未登录三种状态不会互相混淆；
8. 中等与小屏布局不产生横向溢出，操作不遮挡内容；
9. 旧抽屉和 `?ticket=` 详情状态被移除，列表其他行为不回归；
10. 计划内自动化验证通过，并提供非 Production Preview 供用户确认视觉效果。
