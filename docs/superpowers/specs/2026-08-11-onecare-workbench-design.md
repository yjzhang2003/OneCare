# 万护 OneCare：工作台落地设计

- 日期：2026-08-11
- 状态：待用户评审
- 提交截止：2026-08-16 24:00（剩 5 天）
- 前置规格：`docs/superpowers/specs/2026-08-10-onecare-voc-mvp-design.md`（VOC 闭环 MVP，已实施完毕并部署）

## 1. 背景

VOC 闭环 MVP 已经交付并上线：数据在飞书多维表格、AI 打标双轨、飞书卡片内三重校验的工单流转、Cron 分片作业、公开聚合看板。

现在的问题是**落地页形态**：点进飞书应用看到的是方案展示厅（首页 / 四个视角 / 闭环架构 / 团队），而不是一个能干活的工作台。真实数据只在两个角落——公开看板页，以及「四个视角」里的后台视角。

本设计把落地页改成**按身份分流**：外部访客看展示厅，租户成员看工作台。

### 1.1 决策历史（如实记录，避免后人以为这是一次想清楚的设计）

这个方向经历了三次反转：先是「公开工作台、只出聚合」，再是「不做登录、公开全量明细」，最后定为「按身份分流」。第二版被否决的原因值得留下：**公开页面展示记录级 VOC 数据意味着用户原文进公网**，而 VOC 原文是用户手打的自由文本，含姓名、电话、地址、订单号的可能性很高，仓库与站点都是 public。

第三版把这个矛盾整个解掉了——记录级数据永远不出公网，所以不需要靠脱敏去兜一个本不该公开的页面。

## 2. 路由与身份分流

```
/                无会话 → 展示厅（现有四个整屏页面，一行不改）
                 有会话 → 工作台（全量数据）

/showcase        不新建。展示厅仍然由 / 在无会话时渲染

/dashboard/voc   移除，重定向到 /
                 **必须写在 `next.config.ts` 的 `redirects()` 里，不得写成页面级 `redirect()`。**
                 在 `cacheComponents: true` 下，只含一行 `redirect()` 的页面会被静态预渲染，
                 跳转被烘成客户端 meta-refresh，非 JS 客户端拿到 200 而不是真实重定向。
                 `/dashboard` 已经踩过一次并修好，不要重犯。
                 `export const dynamic` 与 `export const runtime` 在 cacheComponents 下均被拒，
                 逐页面的逃生舱不存在。

/api/voc/dashboard  改为需要会话，无会话返回 401

/login           保留不动（飞书体验入口，机器人说明仍在用）
/dashboard       保留现有的 307 → /login
```

同一个 URL 两套界面。展示厅上加一个「进入工作台」入口触发登录；在飞书客户端内打开时静默授权，成员点应用图标基本无感直达工作台。

**外部访客看到的与现在完全一致**，所以对着提交文档过来的读者、以及不愿登录的评委，交付叙事没有损失。

## 3. 租户归属如何被证明

**本应用是企业自建应用（Custom App），只存在于自己的企业内。外部租户的用户无法对它完成 OAuth——应用对他们不存在。**

因此「成功完成 OAuth」本身即是租户归属的证明，不需要维护成员白名单。这比自己维护名单可靠：名单会过期、会漏更新，而应用的租户边界由飞书平台保证。

> **待实现时验证**：`/authen/v1/user_info` 是否同时返回 `tenant_key`。若返回，则额外钉一道等值校验作为纵深防御（防止未来应用被改成商店应用而边界失效）。主保证不依赖这一条，所以它的有无不阻塞本设计。

## 4. 工作台内容

登录后可见，从上到下：

**指标条** — 复用已有的 `aggregateVocMetrics`：总量、中差评占比、待跟进、跟进中、待闭环、已闭环、闭环率、平均闭环时长、打标成功率。

**分布** — 情绪极性分布、问题维度 Top N、渠道分布。`VocMetrics` 已经产出这三项。

**只读工单列表**（本次新建的主体）

| 列 | 来源 |
| --- | --- |
| 反馈时间 | `feedbackAt` |
| 渠道 / 产品品类 | 枚举 |
| 原始内容 | **真实原文，不脱敏** |
| 情绪极性 / 问题维度 / 严重度 | 枚举 |
| 流程状态 | 枚举 |
| 负责人 | **真实姓名** |
| 建单时间 / 闭环时间 / 时长 | 派生 |

**因为已经门禁，展示真实原文与真实姓名。** 运营要看真实反馈才能干活，这正是门禁存在的意义。脱敏函数 `redactVocContent` 在本设计中**仍然不接入任何路径**——它保护的是「数据进入公网」这个场景，而本设计通过门禁消除了该场景。README 关于它的表述维持现状（如实说明它已实现、有测试、但不在任何生产路径上）。

筛选：流程状态、情绪极性。排序：反馈时间、严重度。

**只读。网页上不能改状态。** 改状态只在飞书卡片里发生——网页看状态、飞书做动作，两个写入口不会互相覆盖。这不是偷懒：卡片侧的身份来自事件签名，Web 侧来自会话，两套身份来源写同一个状态机是并发与鉴权的双重风险，而多维表格没有 CAS。

分页不做。数据量是命题方那份周报，量级不大。真超了再说。

## 5. 接口鉴权

`/api/voc/dashboard` 当前完全公开。本设计后：

- 无会话 → `401`
- 有会话 → 返回聚合 + 列表

会话校验复用现有的 `getCurrentSession()`（`src/features/auth/current-session.ts`），不新造。

响应体在有会话时包含记录级字段，这是有意的——它只服务已鉴权的工作台。

## 6. 域名统一（阻塞性前置条件）

登录回到范围内，会话 cookie 的 host-only 性质随之成为阻塞项：

```
网页应用主页        onecare.ohmyfeishu.top
FEISHU_REDIRECT_URI  onecare-loop.vercel.app     ← 实测确认
会话 cookie          无 domain，host-only（cookies.ts:39-45）
```

不统一的后果：用户从 `ohmyfeishu.top` 触发登录 → 回调落在 `vercel.app` → cookie 种在 `vercel.app` → 回到 `ohmyfeishu.top` 仍未登录 → 再次跳登录 → **无限循环**。

**必须三处对齐到 `onecare.ohmyfeishu.top`**：

1. Vercel Production 的 `FEISHU_REDIRECT_URI`
2. 飞书后台「安全设置 → 重定向 URL」登记新地址
3. 网页应用配置的桌面端与移动端主页

选自定义域名而非 `*.vercel.app`：机器人卡片的「打开网页演示」按钮（`cards.ts:20`）与事件回调本就使用它，统一后整个应用只有一个域。

**回调落地点要改**：现在固定跳 `/login`（`callback/route.ts:37,69`），工作台上线后应跳回 `/`。

## 7. 不改动的范围

`src/features/voc/`、`src/features/bitable/`、`src/features/tagging/`、`src/features/feishu-bot/` 一律不动。闭环逻辑与飞书侧已稳定并经真实验证，本次是展示层加一层身份分流。

`/login` 页保留。`/dashboard → /login` 的 307 保留。

## 8. 错误处理

- 指标或列表读取失败 → 复用已有的「指标暂不可用」态（`VocMetricsResult` 的 `unavailable` 分支），**不渲染 0 或占位数字**
- 读取失败**不得**让页面或构建失败——`cacheComponents` 下 `use cache` 函数内部抛出是构建级致命错误，这一点前面踩过，必须在缓存函数内部 try/catch
- 无会话访问 `/` → 渲染展示厅，**不是**重定向到登录页（重定向会让外部访客进不去）
- OAuth 失败 → 落回展示厅并显示错误提示，复用现有的 `errorMessages` 映射

## 9. 缓存

沿用看板现有做法：`use cache` + `cacheLife`，但要分清两层：

- **页面 `/` 本身是动态的**，因为它读 cookie 判断会话（`getCurrentSession()` 已经让它动态渲染）。不要试图缓存整页。
- **被缓存的只有数据读取函数**——一次 `listRecords` 同时产出聚合与列表，包在 `use cache` 里。

缓存是**服务端共享缓存**，所有登录用户看到同一份快照。这可以接受，因为数据本就是全租户共享的运营视图。但**缓存键里不得含任何会话相关的东西**——否则要么缓存命中率崩塌，要么一个用户的视图被另一个用户看到。

失败也会被当作一次成功结果缓存（既有行为），所以一次瞬时故障会让「暂不可用」维持一个 `cacheLife` 窗口，访客刷新绕不过共享缓存。这一点已知并接受。

## 10. 测试

- `/` 无会话 → 渲染展示厅，不含任何工单列表标记
- `/` 有会话 → 渲染工作台，含列表
- `/api/voc/dashboard` 无会话 → 401，且**不触达 Bitable**
- `/api/voc/dashboard` 有会话 → 含聚合与列表
- 读取失败 → 工作台显示「暂不可用」，页面仍 200，不含 0 占位
- 列表筛选与排序的纯函数单测
- 现有 531 单测 + 5 runtime 测试一条不能红

## 11. 前置规格的反转

`docs/superpowers/specs/2026-08-10-onecare-voc-mvp-design.md` §1.4 写着「网站 OAuth 登录与角色：评委已在同一企业内，登录不再是访问前提」。

**本设计反转这一条**，理由是当时的前提变了：那时没有承载记录级数据的页面，现在有了。工作台展示真实原文与真实姓名，登录成为访问前提。外部访客走展示厅，交付叙事不依赖登录。

前置规格需同步标注该反转，README 与 `AGENTS.md` 一并更新。**不允许文档与实现再次背离**——这正是最终评审抓到的问题类型。

## 12. 验收标准

1. 外部（无会话）访问 `/` 看到的展示厅与当前完全一致
2. 租户成员登录后访问 `/` 看到工作台，含真实工单列表
3. 飞书客户端内点应用图标可直达工作台（静默授权）
4. `/api/voc/dashboard` 无会话返回 401 且不触达 Bitable
5. `/dashboard/voc` 重定向到 `/`
6. 指标读取失败时工作台显示「暂不可用」，不显示 0 占位，页面仍 200
7. 三处域名已对齐，登录不产生跳转循环
8. `npm test`、`npm run test:runtime`、`npm run lint`、`npm run typecheck`、`npm run build` 全绿；两条坏凭据构建仍 exit 0
9. 前置规格 §1.4、README、`AGENTS.md` 的表述与实现一致
