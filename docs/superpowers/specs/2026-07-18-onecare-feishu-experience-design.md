# 万护 OneCare 飞书体验入口与轻量机器人设计

## 状态

本规格记录 2026-07-18 对方案一“网站引导页 + 飞书机器人”的确认设计。用户已确认：当前飞书内尚无可用的 OneCare 机器人；本轮先完成一版可评审实现，网站负责加入组织、验证身份和体验引导，飞书机器人负责承载真实对话体验。系统仍是单企业比赛演示，不把机器人描述为生产服务系统。

## 背景与问题

当前网站已经实现飞书企业自建应用 OAuth，但所有“飞书登录”按钮直接跳转 `/api/auth/feishu/start`，没有独立登录页面。登录成功后进入 `/dashboard` 静态工作台，而该工作台与首页四角色 Demo 重复，也没有提供新的产品体验。

当前应用为企业自建应用，只有同时满足以下条件的用户可以登录或使用机器人：

1. 已加入该应用所属的 OneCare 企业；
2. 位于应用已发布版本的可用范围内。

用户已提供 OneCare 企业邀请二维码。二维码显示：仅支持区号为 `+86` 的手机号加入，失效日期为 2026 年 8 月 29 日。该二维码将公开展示在网站，因此页面必须明确它是比赛体验组织，并提示加入申请可能需要管理员审核。

## 目标

本轮建立一条准确、可演示的飞书体验路径：

1. 访客从首页或角色工作台进入独立飞书体验页；
2. 非企业成员可扫码加入 OneCare 组织；
3. 企业成员通过现有 OAuth 验证飞书身份；
4. 登录成功后留在体验页，不再进入重复的静态 Dashboard；
5. 用户在飞书内搜索 OneCare 机器人并完成一轮“知识库自助优先、未解决再转人工”的确定性服务对话；
6. 客服、工程师和后台视角清楚说明未来将在飞书中承接的任务，并提供统一“登录体验”入口。

## 非目标

本轮不实现：

- 真实大模型、RAG、知识库检索或 IoT 数据读取；
- 真实客服工单、工程师调度、配件库存、回访或 VOC 写入；
- 机器人多轮会话持久化、数据库、队列或跨租户数据模型；
- 商店应用、跨企业安装或外部用户机器人共享；
- 在登录后新建另一套网站工作台；
- 将当前浏览器内四视角状态与飞书机器人状态实时同步；
- 在受 Vercel Deployment Protection 保护的 Preview 上声称真实飞书回调已经可用。

## 产品信息架构

### 首页入口

首页 Top Bar 和 Hero 中的未登录 CTA 不再直接访问 OAuth Route Handler，而是统一进入 `/login`：

- Top Bar：`飞书体验`
- Hero：`使用飞书体验`

已登录状态也进入 `/login`，按钮显示 `飞书体验`，由体验页展示身份已验证状态。这样所有用户都能看到扫码加入、登录和打开机器人的完整说明。

### 独立体验页 `/login`

体验页继承现有品牌系统：MiSans、黑色顶部与底部、白色主体、海信青强调色、白色圆角内容容器、圆形或药丸形按钮。页面不使用巨大的稀疏中文标题。

桌面端采用左右两栏，移动端按步骤顺序纵向排列。

#### 左侧：三步进入 OneCare

1. `加入体验组织`：说明未加入 OneCare 企业时先扫描右侧二维码；
2. `验证飞书身份`：使用现有 OAuth 验证所属企业与身份；
3. `在飞书开始体验`：登录后打开飞书并搜索 `OneCare`。

未登录状态显示主按钮 `使用飞书验证身份`，链接到 `/api/auth/feishu/start`。

已登录状态显示：

- 飞书头像或姓名首字；
- 用户姓名；
- `飞书身份已验证`；
- 主操作说明 `打开飞书，在顶部搜索「OneCare」开始体验`；
- 次操作 `退出登录`。

在机器人尚未完成线上发布或搜索入口尚未可用时，页面使用 `机器人配置中` 的准确状态，不显示一个无法工作的“打开机器人”深链。完成发布并取得稳定应用链接后，可在后续小改中把说明升级为直接打开按钮。

#### 右侧：企业邀请二维码

使用用户提供的完整二维码截图，仓库内重命名为无个人设备信息的静态资源：

`public/images/feishu/onecare-enterprise-invite-2026-08-29.png`

图片保留飞书品牌、邀请人、OneCare 企业名、二维码、`+86` 限制和失效日期。页面文字补充：

- `比赛体验组织`
- `仅支持 +86 手机号`
- `二维码有效期至 2026 年 8 月 29 日`
- `加入申请可能需要管理员审核`

不从二维码反解或在代码中保存邀请链接；失效后必须替换资源和页面日期。

### 旧 Dashboard

`/dashboard` 不再作为登录后的产品落点。保留 Route 兼容，但无论是否登录均重定向到 `/login`：

- 未登录用户在 `/login` 看到验证按钮；
- 已登录用户在 `/login` 看到身份已验证和飞书体验说明。

原 Dashboard 展示组件可以暂时保留在仓库中，避免本轮混入大范围删除；页面 Route 不再渲染它。后续确认无引用后再单独清理。

## 三角色飞书体验入口

新增可复用 `FeishuExperienceBanner`，只出现在客服、工程师和后台三个全屏工作台，不放在用户手机 Demo 内。Banner 放在各工作台状态栏下方、主要内容区上方，保证进入角色后无需滚动即可看到。

统一结构：

- 小标签：`计划接入飞书`
- 一句角色化价值说明；
- 药丸按钮：`登录体验`
- 链接：`/login?from=<role>`

三种文案：

- 客服：`在飞书接收转人工会话与 AI 预诊摘要`
- 工程师：`在飞书接收工单、配件与上门提醒`
- 后台：`在飞书接收 VOC 异常与闭环任务`

`from` 只用于体验页显示来源提示，不参与认证授权、租户判断或服务端权限控制。缺失或非法值时忽略，严禁将它用作可信身份输入。

## 轻量机器人 MVP

### 体验范围

机器人使用与网站 OAuth 相同的飞书企业自建应用。用户在飞书中向 OneCare 发送文本消息，机器人完成一条固定、可重复的服务自助路径。

第一版只支持单聊文本，不读取群聊消息，不申请群组全量消息等敏感权限，不处理图片、文件、语音或富文本。

### 对话脚本

机器人按当前网页用户视角的业务叙事提供无状态文本菜单：

1. 用户发送 `开始体验`、`开始`、`你好` 或任意无法识别的文本；
2. 机器人说明检测到冷藏室温度持续偏高，并给出选项：
   - `1 饮料不够凉`
   - `2 刚才开始`
   - `3 没有影响`
3. 用户回复 `1`、`2`、`3` 或对应文本；
4. 机器人返回三条知识库排查建议，并提示回复：
   - `已解决`
   - `转人工`
5. 用户回复 `已解决` 时，机器人确认本次问题已由自助解决；
6. 用户回复 `转人工` 时，机器人生成固定预诊摘要，说明已为客服准备设备、现象和建议配件信息；
7. 用户随时发送 `重新开始` 回到第一步。

该流程不保存会话阶段。每条消息通过关键词独立决定回复，因此适合无数据库 Vercel Serverless MVP，也不会把临时内存误当成可靠持久化。回复必须注明 `演示流程`，不得声称真实工单已经创建。

### HTTP 数据流

新增公开 Route Handler：

`POST /api/feishu/events`

职责：

1. 读取原始请求体；
2. 使用飞书官方 Node SDK 的事件分发能力校验 Verification Token，并在配置 Encrypt Key 时完成解密；
3. 处理飞书 URL Verification challenge；
4. 仅接受 `im.message.receive_v1` 且 `chat_type=p2p` 的文本消息；
5. 立即接受合法事件，并将回复消息作为短任务执行；
6. 使用应用身份获取 tenant access token；
7. 调用回复消息 API，以原 `message_id` 回复用户；
8. 对非法签名、错误事件类型和畸形内容返回安全错误，不记录消息正文、令牌或密钥。

飞书要求事件回调在三秒内返回 HTTP 200。实现不得等待模型推理；机器人回复使用固定脚本和短超时。若 Vercel/Next.js 运行时提供经过验证的请求后任务机制，可先确认事件后发送回复；否则以明确的小于三秒请求预算同步完成，并将超时作为可观测但不泄密的失败。计划阶段必须通过当前 Next.js 与 Vercel 官方文档选择其中一种，不凭记忆决定。

### 消息回复适配器

新增独立 TypeScript 模块，避免 Route Handler 包含业务脚本：

- `bot-script.ts`：纯函数 `createBotReply(text)`，输入用户文本，输出确定性回复；
- `feishu-bot.ts`：tenant token 与回复消息 API 适配器；
- `event-handler.ts`：事件验证、解析和安全错误映射；
- Route Handler：HTTP 编排。

外部请求通过注入 `fetch` 测试，不在单元测试访问真实飞书。

### 环境变量

复用：

- `FEISHU_APP_ID`
- `FEISHU_APP_SECRET`

新增：

- `FEISHU_EVENT_VERIFICATION_TOKEN`
- `FEISHU_EVENT_ENCRYPT_KEY`

所有变量均为服务端变量，不使用 `NEXT_PUBLIC_*`。Verification Token、Encrypt Key、App Secret、tenant token 和用户消息不得进入 Git、客户端 Bundle、URL、错误页面或普通日志。

## 飞书后台配置

代码完成后仍需在当前企业自建应用中完成以下外部配置：

1. 添加机器人能力，并设置机器人名称与图标；
2. 开通最小的“读取用户发给机器人的单聊消息”和“以应用身份发送/回复消息”权限；
3. 配置 `im.message.receive_v1`；
4. 将稳定、公开、不受 Vercel Deployment Protection 阻挡的地址配置为事件请求 URL：
   `https://onecare-loop.vercel.app/api/feishu/events`；
5. 将同一 Verification Token 与 Encrypt Key 写入 Vercel Production 敏感环境变量；
6. 创建并发布应用版本；
7. 将应用可用范围覆盖所有允许参加比赛体验的 OneCare 成员；
8. 使用真实企业成员完成单聊、回复与 OAuth 回归验收。

Preview 只用于页面视觉、路由和本地模拟验收。Vercel 分享链接携带的访问凭证不能作为飞书事件回调认证方式。真实机器人必须等 Production 部署和飞书后台配置完成后才能宣称可用。

## 安全与隐私边界

- 邀请二维码由用户明确提供并授权公开展示；页面必须显示失效日期和审核提示。
- 建议在飞书管理后台开启加入审核，避免公开二维码自动扩大企业成员范围。
- OAuth 继续使用一次性 state、服务端 token exchange 和 HttpOnly 签名会话。
- 企业成员身份和应用可用范围仍由飞书验证，不以 `from`、Query、Cookie 自报组织信息为依据。
- 机器人事件必须验证来源，缺少验证配置时拒绝启动或返回安全配置错误。
- 只处理单聊文本，最小化消息权限和数据接触面。
- 不持久化消息正文、open_id、tenant token 或飞书用户 access token。
- 不在日志输出请求体；可记录脱敏事件类型、请求结果和内部错误码。
- 当前无可靠事件去重存储。固定回复是幂等业务内容，但极端重试可能产生重复消息；真实业务接入前必须增加持久化 event_id 去重。

## 视觉与组件复用

- 新登录页复用现有 `OneCareLogo`、全局字体、颜色 Token、药丸按钮和圆角卡片规则。
- 新增共享 `FeishuExperienceBanner`，禁止在三个角色组件内复制结构与样式。
- 所有文字按钮保持药丸形、文字居中、无箭头，只使用现有颜色反转动效。
- 二维码卡片保持白底，不添加可能影响扫描的滤镜、遮罩或动画。
- 登录页桌面与移动端都必须完整显示二维码静区。
- 三角色 Banner 不得改变现有全屏工作台的页面高度或造成横向溢出。

## 错误处理

### 登录页

- 已知 OAuth 错误继续显示安全中文提示；
- 配置缺失时不显示密钥或内部响应；
- 二维码资源加载失败时显示文字加入说明和失效日期，不显示破损布局；
- `from` 非法时静默回到通用标题。

### 机器人

- URL Verification challenge 必须返回飞书要求的结构；
- 验证失败返回 401 或 403，不回复消息；
- 非文本、群聊或未支持事件返回 200 并忽略，避免无意义重推；
- tenant token 或回复 API 失败时返回/记录稳定内部错误码，不记录上游响应体；
- 不把 App Secret、Verification Token、Encrypt Key、tenant token 或消息正文写入错误。
