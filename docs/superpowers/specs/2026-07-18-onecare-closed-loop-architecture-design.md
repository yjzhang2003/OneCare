# 万护 OneCare AI 用户服务闭环架构设计

## 状态与优先级

本规格定义万护 OneCare 展示站当前“02 · 五层引擎”一级页面的内容与表现调整。它以 2026-07-18 的 `origin/main`（`0663447`）为代码基线，继承现有整屏章节导航、黑白品牌展厅、MiSans、青绿色强调、药丸按钮、圆角白卡和静态演示边界。

本规格已于 2026-07-18 完成用户审核。实施必须先编写计划，并遵循 RED → GREEN → REFACTOR；本任务不授权 Vercel 或 Production 操作。

如果本规格与旧的五层架构展示结论冲突，以本规格为准；首页、四个视角、团队、Dashboard、飞书认证和部署相关规则不受影响。

## 代码基线与当前页面

### 一级导航与页面归属

- `src/features/showcase/navigation.ts` 的 `showcasePages` 把第三个一级页面定义为 `{ id: "architecture", label: "五层引擎", index: "02" }`。`ShowcaseNavigator`、Hash 恢复和整屏切换都依赖稳定的 `architecture` ID，而非中文名称。
- `src/features/showcase/components/showcase-navigator.tsx` 将四个一级页面作为独立滚动容器长期渲染，并用 `before / active / after`、`inert` 和 `aria-hidden` 管理方向与可访问性。
- `src/features/showcase/components/site-header.tsx` 从 `showcasePages` 生成顶部导航；`src/features/showcase/components/site-footer.tsx` 仍单独写有“五层引擎”页尾入口。
- `app/landing-content.tsx` 在 `pages.architecture` 中依次组合五层蓝图和方案目标，页面仍使用 `#architecture`、编号 `02`，且位于“四个视角”和“团队”之间。

### 内容与数据

- `src/features/showcase/content.ts` 通过 `ServiceLayer`、`ScenarioStep` 和 `Outcome` 三个只读类型，集中提供 `serviceLayers`、`scenarioSteps` 和 `outcomes`。
- `serviceLayers` 固定为“感知—诊断—编排—服务—学习”，每层只有输入、系统动作和输出；`scenarioSteps` 把冰箱温控异常映射到五层；`outcomes` 只表达“更短服务周期 / 更低重复上门 / 更高用户满意”。
- 当前结构没有统一用户 ID、设备 ID、服务事件 ID，也没有数据与知识层、智能编排层、多角色应用层、人工审核分支、异常介入、四项六个月试点目标或渐进式接入路径的表达位置。
- `src/features/showcase/perspective-demo-data.ts` 和 `src/features/showcase/service-journey.ts` 已为“四个视角”提供统一案例 `OC-240718-037` 与浏览器内确定性状态机，但它们服务于可点击 Demo，不应被架构页误写成真实后端数据源或生产事件模型。

### 组件、视觉与响应式

- `src/features/showcase/components/service-blueprint.tsx` 将五层渲染为一个有序列表，桌面五列、移动端单列，并用节点路径和“学习结果回到感知”说明回流。
- `src/features/showcase/components/outcome-statement.tsx` 只接受强调词与标签，适合三段定性目标，不足以承载四项带百分比的试点目标、时间范围和目标免责声明。
- `app/globals.css` 已把蓝图置于一个白色、浅灰边框、`28px` 圆角的大面板中，使用青绿色节点和连接线；在 `1100px` 以下转为纵向，在 `640px` 以下把字段改为单列。该视觉语言可继续使用。
- `app/landing-content.test.tsx` 当前锁定“五层引擎”导航、`#architecture`、五层列表的可访问名称、五层顺序和三个定性目标；`app/fullscreen-showcase-styles.test.ts` 锁定整屏视口、移动端高度与减少动效等全站契约，但尚未单独覆盖新架构内容。

## 调整目标

1. 将架构页从五个串行处理阶段改为能准确解释新方案的三层架构。
2. 把统一的用户 ID、设备 ID 和服务事件 ID 作为跨系统连续服务的主线，而不是附加标签。
3. 清楚展示 AI 直接解决与人工审核之间的风险分流，并明确人工仍是复杂、高风险和低置信度问题的执行闸门。
4. 将“智能分流 → 人工审核 → 自动编排 → 异常介入 → 结果反馈与持续优化”表现为跨三层运行的闭环机制，而不是新的“五层系统架构”。
5. 明确所有跨系统、AI、IoT、数据库和指标内容均为拟议方案或试点目标，不暗示已经接入或实现。
6. 在不改变网站整体视觉、一级顺序和交互模型的前提下，让评审在桌面和手机上快速读懂“连接什么、如何决策、如何闭环、如何试点”。

## 一级名称决策

### 采用：“闭环架构”

顶部导航、页尾导航和一级小标题由“五层引擎”改为：

```text
闭环架构
02 · 闭环架构
```

页面主标题建议为：

```text
统一服务事件，驱动三层协同闭环
```

采用理由：

- “闭环架构”同时覆盖三层系统关系和持续反馈机制，不会继续暗示存在五个架构层；
- 比“三层架构”更能表达 OneCare 的核心差异，比“AI 引擎”更少制造 AI 已经上线的误解；
- 与页头现有“AI 用户服务闭环引擎”品牌描述相呼应，但不重复完整产品名；
- 文案长度与现有 Top Bar、移动端四项同排和页尾链接空间相容。

不采用“服务蓝图”，因为该名称更像流程说明，弱化统一标识与跨系统架构；不采用“AI 闭环引擎”，因为它容易让规划能力被理解为已实现产品能力。

`#architecture`、索引 `02`、一级页面顺序及 `ShowcasePageId` 保持不变，避免破坏深链、History、焦点和现有导航模型。

## 页面叙事

2026-07-18 视觉评审后，02 一级页面采用三个内部章节，而不再把全部内容放在一条长页面中：

1. “架构全景”组合统一服务事件、三个关联标识、计划连接端与三层架构，回答系统由什么组成；
2. “闭环运行”组合风险分流、人工审核边界与五步核心闭环，回答系统如何运行；
3. “试点落地”组合四项 6 个月目标、口径声明与三阶段推广路径，回答如何开始验证。

三个章节保留在 `#architecture` 内，不增加路由或一级编号。三个模块全部进入一级页面的连续纵向阅读流，不设置章节内部滚动区；无椭圆外框的文字导航在滚动后吸附于页面顶部，点击可滚动至对应模块，页面越过章节边界时同步当前高亮。移动端使用同一全局滚动逻辑和单列内容。章节控件仅使用中文，并支持方向键、Home 与 End。

页面按“共同主线 → 三层能力 → 决策治理 → 运行闭环 → 试点落地”的顺序阅读。该顺序在桌面与移动端保持一致，不使用 CSS 改变语义顺序。

### 1. 页面导语：先说明方案边界

建议导语：

> 万护拟通过统一的用户、设备与服务事件标识，轻量连接海信爱家、400 客服、IoT、工程师和备件系统，让一次问题在数据、决策和执行之间连续流转。

导语使用“拟通过”“轻量连接”，不能写成“已经打通”“实时接入”或“已形成生产闭环”。

### 2. 统一服务事件：建立整页主线

在三层架构之前展示一条紧凑的“统一服务事件”身份带，内容包括：

- 用户 ID：识别服务对象；
- 设备 ID：关联设备状态、型号与历史；
- 服务事件 ID：串联本次问题从发现到回访的全部信息；
- 计划连接端：海信爱家、400 客服、IoT 平台、工程师、备件系统。

三种 ID 不是三个独立产品模块，而是同一服务事件的关联键。视觉上应汇入一条贯穿后续三层和闭环的青绿色主线，并明确标注“方案中的统一关联标识”。

三种 ID 只显示中文名称，不增加英文辅助标签，以保持与网站其他一级内容一致。“海信爱家”在计划连接端中使用正式字标；素材必须来自可核验的官方来源，并在现有素材清单中记录来源、获取日期和用途。其他连接端继续使用中文文本，不为本页新增一套图标系统。

### 3. 三层架构：解释各层职责

采用一个大型圆角系统面板，内部包含三个连续层带；不拆成三张悬浮营销卡。DOM 与阅读顺序固定为基础到应用：

#### 数据与知识层

- 汇聚范围：设备运行数据、用户反馈、历史工单、备件库存、产品说明书和维修案例；
- 关键作用：形成可检索的服务知识与事件证据；
- IoT 价值：基于异常趋势形成设备健康预警线索；
- 边界文案：均为计划接入与计划能力，不写成实时数据湖、生产知识库或已上线预警。

#### 智能编排层

- 多模态问诊；
- 问题分级与置信度判断；
- 结构化工单生成；
- 工程师与配件匹配；
- 服务全流程追踪和异常触发。

该层是新页面的视觉中心，但必须同时出现人工审核闸门，避免把编排描绘成无人监督的全自动系统。

#### 多角色应用层

- 用户：自助服务、问题补充、进度与结果确认；
- 客服：审核服务方案、补充判断、协同派单；
- 工程师：查看诊断与历史、核验配件、记录维修结果。

只展示本方案中的角色价值，不复刻“四个视角”页面的完整工作台，也不新增后台角色交互。

每一层使用清楚的层名、一句职责和短列表；不沿用旧蓝图的“输入 / 系统动作 / 输出”三栏机械重复，以避免在手机上形成冗长字段墙。

### 4. 风险分流与人工审核：说明决策边界

三层面板之后展示一个静态双路径决策区：

- 标准化、低风险且置信度达到规则要求的问题：AI 提供自助建议并由用户确认结果；
- 复杂、低置信度或高风险问题：形成服务方案，包含用户描述、设备数据、历史记录和已完成操作，经人工审核后再执行。

两条路径都回到同一个服务事件。人工路径必须在视觉和语义上明确显示“审核后执行”；不得出现“AI 自动审批高风险问题”“全自动派单”等表述。

本区为说明性内容，不增加按钮、Tab 或客户端状态。这样既避免与“四个视角”Demo 重复，也确保无 JavaScript 时仍能完整阅读。

### 5. 核心闭环：解释跨层运行机制

使用一个有序列表展示固定五步：

1. 智能分流；
2. 人工审核；
3. 自动编排；
4. 异常介入；
5. 结果反馈与持续优化。

这五步是服务事件的运行闭环，不称为“五层”。闭环说明应覆盖：

- 持续追踪派单、备件、上门、维修和回访；
- 计划在超时、资源不匹配或执行异常时触发人工介入；
- 利用客服对话、维修结果和回访反馈，持续优化问诊规则与维修知识。

现有 `ServiceBlueprint` 的节点连接和移动端纵向路径可以作为视觉参考，但语义和组件接口需要改变。

### 6. 六个月试点目标：量化但不成果化

独立标题固定为“6 个月试点目标”，并在指标之前显示：

> 以下为试点目标区间，不代表已经取得的生产结果；实际基线和测量口径需在试点启动前确认。

展示四项指标：

| 指标 | 目标 |
| --- | --- |
| 首次有效响应时间 | 相对降低 30%–50% |
| 人工工单整理时间 | 承诺降低 35%，拉伸至 40% |
| 平均服务周期 | 承诺缩短 15%，拉伸至 20% |
| 30 日重复上门率 | 相对降低 15% |

视觉可复用当前 `OutcomeStatement` 的大号文字和分隔线节奏，但应改为四项响应式网格，并把“目标”与指标名称组合为完整可访问文本。不得使用达成进度、绿色对勾、已完成状态或虚构基线。

四项指标共用网格上方单独显示的一处“试点目标”小标题，不在每项中重复显示同名标签。每项按“指标名称 → 主目标 → 可选拉伸目标”组织；人工工单整理时间和平均服务周期的“拉伸至”目标独立显示在主目标下一行，其余两项不保留空占位。

### 7. 试点路径：用阶段收束页面

在指标后用一条简短阶段带收束：

```text
API 轻量接入 → 单一重点产品 × 代表性区域 → 验证后逐步推广
```

该阶段带必须使用“计划”“试点”“验证后”等措辞。它只表达落地策略，不实现 API、数据库、IoT 或外部系统连接。

## 组件与数据方案

### 数据模型

`src/features/showcase/content.ts` 继续存放只读静态内容，但建议以职责清晰的类型替换旧模型：

- `ServiceIdentity`：用户 ID、设备 ID、服务事件 ID；
- `ConnectedSystem`：计划连接端与其作用；
- `ArchitectureLayer`：层名、职责和能力列表；
- `DecisionPath`：适用条件、处理方式和人工边界；
- `ClosedLoopStep`：顺序、名称和作用；
- `PilotTarget`：指标、方向、数值和试点状态；
- `RolloutStage`：轻量接入、聚焦试点、逐步推广。

所有文案使用 `readonly` TypeScript 常量；不读取当前时间、不生成随机数据、不发起网络请求。

### 组件边界

推荐对架构页做局部语义重构：

- 以 `ArchitectureChapters` 组合三个连续章节并管理滚动联动导航；`ServiceArchitectureOverview` 负责统一事件带和三层架构，`ServiceLoopMechanism` 负责决策分流和闭环步骤；
- 以新的 `PilotTargets` 组件替代或语义化重构 `OutcomeStatement`，负责四项试点目标与免责声明；
- `LandingContent` 只负责章节标题、组件组合和试点路径，不在 JSX 中散落大段架构数据；
- `ShowcaseNavigator`、`ShowcasePageHeading`、`SectionFrame`、`SiteHeader` 的结构与行为保持不变；
- `SiteFooter` 只同步可见导航名称，不改变页尾结构。

如果实施审核认为重命名文件会增加无意义变更，可以保留文件路径，但导出的组件名、props 与可访问名称必须反映“三层闭环架构”，不得继续暴露“五层蓝图”语义。禁止把所有区块抽象成高度参数化的万能卡片。

## 视觉延续方式

### 桌面

- 白色页面画布不变；主内容继续放在一个 `28px` 圆角、浅灰描边的大型系统面板内；
- 三层使用连续水平层带，统一服务事件主线沿面板一侧或中轴贯穿，不做三张浮起卡片；
- 数据与知识层、智能编排层、多角色应用层使用同一视觉系统，通过层号、留白和青绿色节点区分；
- 决策分流使用两条克制的线性分支，其中人工审核路径具有清楚文字标识，不只依赖颜色；
- 五步闭环可沿单一路径排列，并用回流说明连接“结果反馈与持续优化”与下一次“智能分流”；
- 四项目标使用四列线性分隔；试点路径使用一条轻量阶段带，不增加新卡片层级。

### 平板与手机

- 三层、决策路径、五步闭环和试点路径全部转为单列或纵向路径，DOM 顺序不变；
- 统一服务事件身份带允许换行，但每个 ID 标签与说明作为完整语义单元，不横向挤压；
- 指标在平板可两列、手机单列，不使用必须横滑才能读取的核心信息；
- 正文不小于 `16px`，辅助说明不小于 `14px`，触控区域规则继续适用于导航；
- 页面级不得横向溢出，长系统名称允许自然换行；

## 风险与缓解

### 规划能力被误读为已实现

风险最高。所有跨系统、AI、IoT、知识库、库存、追踪和优化文案都必须使用“拟”“计划”“试点目标”等状态词；页尾现有原型边界继续保留。测试应锁定关键免责声明。

### “三层”与“五步”再次混淆

三层只回答系统职责，五步只回答服务事件如何运行。标题、可访问名称和数据类型必须分开，禁止使用同一个 `ServiceLayer` 结构承载两者。

### 信息密度过高

统一事件、三层、双路径、五步闭环、四项目标和三阶段试点均为必需信息。通过三个中文章节、短句和开放式分组控制密度；所有内容均可通过明确可见的章节导航访问，不使用悬浮卡片或长段技术说明。

### 新名称影响深链或导航

只改可见 label，不改 `architecture` ID、索引或页面顺序。导航和 History 回归测试必须继续通过。

### 试点指标缺少基线与口径

当前只展示用户提供的目标值，不补造绝对基线、样本量、统计口径或达成进度。页面明确说明口径需在试点启动前确认。

### 局部组件重构扩大范围

只重构架构页使用的旧五层组件和目标组件。共享导航、四视角状态机、认证与 Dashboard 不动；实施计划应为每个新组件给出明确替换和删除路径。
